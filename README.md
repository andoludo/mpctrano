# mpctrano

**Calibration, state estimation and economic model predictive control (MPC) of the RC building
models generated by [Trano](https://github.com/andoludo/trano).**

Trano turns a YAML description of a building into Modelica models. With its `mpc` library it
generates a flat resistance-capacitance (RC) model, `building_mpc`, together with a JSON
interface listing its states, inputs and parameters. mpctrano takes those two artefacts and:

1. **calibrates** the RC parameters on monitoring data of the real building (IPOPT least squares),
2. **estimates** the unmeasured states (Kalman filter or moving horizon estimation),
3. **controls** the heating of each zone with an economic MPC that keeps comfort at the lowest cost
   under a tariff: flat, time-of-use, day-ahead prices, demand response events or a capacity charge,
   which exposes the **flexibility** of the building to the grid.

Everything is symbolic: [rumoca](https://github.com/rumoca/rumoca) translates the Modelica model
into a [CasADi](https://web.casadi.org/) ODE whose parameters stay free, and the same CasADi
functions serve the calibration, the estimators and the controller. All optimisation problems are
solved with [IPOPT](https://coin-or.github.io/Ipopt/).

```
 house.yaml ──trano──▶ house.mo + house.mpc.json ──rumoca──▶ CasADi ODE  xdot = f(x, u, d, p)
                                                                 │
   monitoring.csv ──▶ MonitoringData ──▶ Calibrator (IPOPT) ──▶ calibrated p
                                                                 │
   weather .mos + occupancy ──▶ WeatherForecaster ──▶ d(t)       │
   tariff + comfort band ──────────────────────────▶ ModelPredictiveController (IPOPT)
   measured zone temperatures ──▶ KalmanFilter / MHE ──▶ x̂ ──▶ heating power of each zone
```

## Quick start

```python
from mpctrano import Project, MonitoringData, scenario_catalogue, compare

project = Project.from_yaml("house.yaml")  # Trano generates the RC model (R3C2 by default)
data = MonitoringData.from_csv("monitoring.csv", temperature_unit="C")
result = project.calibrate(data, validation_fraction=0.25)
print(result.metrics())  # RMSE before/after, training and validation

catalogue = scenario_catalogue(start="2023-01-16", days=2)
runs = {name: project.run(catalogue[name]) for name in ("flat", "time_of_use", "dynamic_price")}
print(compare(runs, baseline="flat"))  # cost, energy, comfort, peak, shifted energy
```

The same steps from the command line:

```bash
mpctrano generate house.yaml                                   # house.mo + house.mpc.json
mpctrano synthetic-data house.yaml --output monitoring.csv     # data of a perturbed copy, to try the package
mpctrano calibrate house.mo monitoring.csv                     # house.calibrated.mpc.json
mpctrano run house.yaml --calibrated house.calibrated.mpc.json --scenario time_of_use --days 2
mpctrano scenarios
```

No real building at hand? `Project.true_building()` perturbs the Trano parameters into a
synthetic "real" building and `Project.synthetic_data()` records monitoring data on it with a
randomised thermostat; this is what the tests and the tutorials use.

## Monitoring data

A regularly sampled CSV (or `DataFrame`) whose columns are named after the interface signals:

| Column               | Unit | Role                                                      |
|----------------------|------|-----------------------------------------------------------|
| `time`               |      | timestamp (first column by default)                       |
| `<zone>_Ti`          | K/°C | measured air temperature of a zone (at least one zone)    |
| `<zone>_QHea`        | W    | heating power delivered to the zone (control input)       |
| `TOut`               | K/°C | outdoor temperature                                       |
| `HSol_<orientation>` | W/m² | total irradiance on an orientation (optional)             |
| `<zone>_QInt`        | W    | internal gains (optional)                                 |

Disturbances that are not measured are filled from the weather file of the Trano model and the
occupancy schedule of each zone (`MonitoringData.fill_disturbances`). `temperature_unit="C"`
converts the temperature columns on reading; `rename=` maps your headers to the interface names.

## Calibration

`Calibrator` solves a multiple-shooting least-squares problem: the state trajectory and the
parameters are decision variables, the discrete RC dynamics are equality constraints. Parameters
are log-parameterised (`p = p0·exp(z)`) and bounded to a factor range around the Trano initial
guess, with a Tikhonov regularisation towards it: the measured zone temperatures identify the fast
parameters (air capacities, direct losses, solar apertures) while the non-identifiable ones stay at
their physical prior. Unmeasured states are estimated with the parameters. The fit is reported on
the training and on a validation period (`CalibrationResult.metrics()`), and `summary()` shows
which parameters moved and whether one hit a bound.

```python
from mpctrano import Calibrator, CalibrationSettings

settings = CalibrationSettings(parameters=["*_Ci", "*_Ria", "*_gA_*"], lower_factor=0.3, upper_factor=3.0)
calibrated_model, result = Calibrator(model, settings).fit(train, validation)
calibrated_model.write("out", "house")  # house.mo + house.mpc.json with the calibrated values
```

## State estimation

The RC model is linear in the states and the inputs, so `KalmanFilter` uses its exact discrete
affine form. `MovingHorizonEstimator` solves a least-squares problem on a sliding window with
IPOPT. Both use the same cycle in the closed loop: `correct(measurement)` then `predict(u, d)`.

## MPC, tariffs and flexibility

`ModelPredictiveController` minimises, over a receding horizon,

    energy cost (price × energy) + capacity charge × peak power + comfort penalties (soft band)
    + penalty above a demand response power limit + optional ramp penalty

subject to the RC dynamics and the heating power bounds (the design power of each zone from the
Trano interface by default). The problem is built once with CasADi `Opti` and warm started.

Tariffs (`mpctrano.tariff`): `FlatTariff`, `TimeOfUseTariff`, `DynamicTariff` (a price series, e.g.
day-ahead prices from a CSV), `DemandResponseEvent` (price multiplier and/or power cap over a period)
and a `capacity_charge` on the peak. Comfort (`mpctrano.comfort`): occupied/unoccupied bands per
zone; `ComfortSpec.map("widen", 1.0)` opens the band to trade comfort for flexibility.

`scenario_catalogue()` ships ready-made scenarios (`flat`, `time_of_use`, `dynamic_price`,
`demand_response`, `peak_shaving`, `wide_comfort_band`, `imperfect_forecast`);
`compare(runs, baseline="flat")` reports the cost savings, the energy shifted in time, the share of
energy bought below the median price, the comfort violations and the peak power of each run.

## FastModel: the systems of the building (experimental)

Trano's `FastModelMPC` library turns the same YAML into a model close to the Buildings library (layered
walls, windows, radiators, valves, mixing valves, boilers, heat pumps, ventilation, PV) that rumoca
still translates into a CasADi ODE. `FastModel` loads it and `FastModelPredictiveController` controls
it: the controls are those of the systems (valve positions, boiler part load ratio, heat pump speed,
between 0 and 1, or the heat of ideal emitters) and the energy is read from the meters of the model
(fuel, electricity, PV production, in kWh), so the efficiency of the systems is part of the optimisation.

```python
from mpctrano import (ComfortSpec, FastModel, FastModelPredictiveController, FastMPCSettings,
                      FastWeatherForecaster, TimeOfUseTariff)
from mpctrano.fast_simulation import FastModelPlant, PerfectEstimator, run_fast_closed_loop, run_rule_based

house = FastModel.from_yaml("house.yaml")  # trano, FastModelMPC library
house.control_names, house.disturbance_names, house.meters  # read from the Modelica model
forecaster = FastWeatherForecaster.from_model(house)  # weather file and occupancy of the YAML
comfort, tariff = ComfortSpec(), TimeOfUseTariff()
controller = FastModelPredictiveController(house, FastMPCSettings(horizon=24, fuel_price=0.08), comfort, tariff)
plan = controller.solve(house.initial_state, forecaster.forecast(start, 24, 3600))
plan.controls, plan.costs, controller.energy

# one day in closed loop, and the controllers of the YAML (the closed-loop FastModel) as the baseline
plant = FastModelPlant(house, 3600, start)
mpc = run_fast_closed_loop(controller, PerfectEstimator(plant), plant, forecaster, steps=24)
closed_loop = FastModel.from_yaml("house.yaml", library="FastModel")
baseline = run_rule_based(closed_loop, FastWeatherForecaster.from_model(closed_loop), start, 24, 3600, comfort,
                          tariff, fuel_price=0.08)
mpc.summary(), baseline.summary()  # fuel, electricity, cost, comfort, peak, off-peak share
```

The model is nonlinear and stiff (water nodes): it is simulated with CVODES and optimised on Radau
collocation points (`trano.optimization`), with the same objective as the RC controller (tariff,
capacity charge, soft comfort band, demand response limits) applied to the electricity bought from the
grid and the fuel drawn. The solar position is computed inside the model, so the forecast holds the raw
weather channels (`weather_inputs.TDryBul`, `.TBlaSky`, `.winSpe`, `.winDir`, `.HDirNor`, `.HDifHor`,
`.HGloHor`), the sky temperature computed as the Buildings weather reader does, and the radiant and
convective gains per floor area of each occupancy model. The runs are costed from the meters of the
plant, each carrier at its price.

On the single-zone hydronic house of the tests, over a January day with the band of its emission control
(22 degC from 10h to 20h, 18 degC otherwise), the MPC costs 12 % less than the controllers of the YAML
under a flat and under a time-of-use tariff, with almost no discomfort (0.05 K.h against 3.7 K.h, the
warm-up of the rule-based controllers), and buys 30 % of its energy off-peak against 10 %. Each hourly
solve takes 4 to 8 s.

The CasADi export of these models needs rumoca main up to commit `c74cddf`, which is not released on
PyPI: `make rumoca-fastmodel` builds it (Rust toolchain needed), and the FastModel tests are skipped
without it. State estimation (the closed loop uses the true state for now), calibration and the
scenarios of `Project` are the next steps.

## Tutorials

The interactive notebooks on MPC and energy flexibility live in `tutorials/` (see
`tutorials/README.md`). The `tutorials/package/` scripts walk through the package on the three-zone building of the Trano test
suite (`uv run python tutorials/package/01_model_from_trano.py`, figures written to `tutorials/output/`):

1. `01_model_from_trano.py` - generate the model, inspect the interface, simulate it.
2. `02_monitoring_data_and_calibration.py` - monitoring CSV, validation report, calibration, fit plots.
3. `03_state_estimation.py` - Kalman filter vs moving horizon estimation.
4. `04_mpc_comfort.py` - one optimal plan, then closed loop against the "real" building.
5. `05_tariffs_and_flexibility.py` - scenarios, custom tariffs, demand response, comfort band vs cost.
6. `06_full_pipeline.py` - the whole workflow with `Project` in a few lines.

More in `docs/`: [workflow](docs/index.md), [calibration](docs/calibration.md),
[state estimation](docs/estimation.md), [MPC and tariffs](docs/mpc.md), [data format](docs/data.md).
